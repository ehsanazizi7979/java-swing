Creating Your First Window (JFrame & Safe Startup)

Simple goal: Open a real desktop window with a title, size, and working close button—and start it on the right thread.

Simple Analogy: Think of JFrame as an empty picture frame on your desk. Before hanging it up (setVisible(true)), you pick its size, label it, and put everything inside it.

Key Points in Simple Terms

  • extends JFrame makes your class a window: Because StockApp extends JFrame, your app inherits ready-made window powers like a title bar, borders, minimize/maximize buttons, and resizing.
  • Set 3 basic window settings in the constructor:
    • setTitle("Stock Monitor") — puts text in the top title bar.
    • setSize(800, 500) — sets width to 800 pixels and height to 500 pixels.
    • setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE) — tells Java to actually quit the program when you click the red X button (otherwise the window hides, but Java keeps running invisible in the background!).
  • Windows start invisible by default: Nothing appears on screen until you call setVisible(true)—do this last after building your menus and tables so the user doesn't see a half-built blank window.
  • Start Swing using SwingUtilities.invokeLater(...): Swing uses one special worker thread called the Event Dispatch Thread (EDT) to draw everything on screen. Starting your window inside invokeLater guarantees the UI is created safely on that thread.

From Your Code

public class StockApp extends JFrame {
    public StockApp() {
        setTitle("Stock Monitor");
        setSize(800, 500);
        setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE); // Stop program when X is clicked
        ...
    }

    public static void main(String[] args) {
        SwingUtilities.invokeLater(new Runnable() {     // Safely hand work to the UI thread
            public void run() {
                new StockApp().setVisible(true);        // Show window once ready
            }
        });
    }
}
Common Mistake to Avoid: Forgetting JFrame.EXIT_ON_CLOSE. Without it, closing the window leaves your background timer running forever until you force-stop it in IntelliJ.
Lesson 2 src/StockApp.java

Menus, Click Events & Popup Messages

Simple goal: Add a top menu bar (File → Exit, View → Refresh) and make things happen when the user clicks an item.

Simple Analogy: An ActionListener is like a doorbell wired to a button. It sits quietly doing nothing until someone clicks the menu item—then it immediately runs your actionPerformed code.

Key Points in Simple Terms

  • Menus are built in 3 nested layers:
    1. JMenuBar — the horizontal strip across the top of the window.
    2. JMenu — a drop-down category name on that strip (like File or View).
    3. JMenuItem — an actual clickable command inside a menu (like Exit or Refresh).
  • Attach the menu bar with setJMenuBar(...): Notice you use setJMenuBar(bar) rather than add(bar) so Swing reserves the special top slot of the window for it.
  • addActionListener reacts to clicks: You pass an object with an actionPerformed(ActionEvent e) method. Whatever is inside that method runs when the user clicks the item.
  • JOptionPane.showMessageDialog(...) shows quick popups: Great for alerts, confirmations, or placeholders (like "Refresh coming in Step 2").
  • Why StockApp.this instead of just this? Inside new ActionListener() { ... }, plain this refers to the listener itself, not your window! Writing StockApp.this tells Java: "center this popup over my main StockApp window."
  • Clean exit: Before calling System.exit(0), the Exit menu calls executor.shutdown() to politely stop the background timer thread.

From Your Code

JMenu viewMenu = new JMenu("View");
JMenuItem refreshItem = new JMenuItem("Refresh");
refreshItem.addActionListener(new ActionListener() {
    public void actionPerformed(ActionEvent e) {
        // StockApp.this points to the outer JFrame window
        JOptionPane.showMessageDialog(StockApp.this, "Refresh coming in Step 2");
    }
});
viewMenu.add(refreshItem);
Modern Java Bonus Tip: Since your project uses JDK 17, new ActionListener() { public void actionPerformed(ActionEvent e) { ... } } can also be written in one short lambda line: refreshItem.addActionListener(e -> JOptionPane.showMessageDialog(this, "...")); — and inside a lambda, plain this automatically means StockApp!
Lesson 3 src/Stock.java

Modeling Your Data Cleanly (Stock & enum)

Simple goal: Keep business data and rules in their own plain Java class (Stock.java) instead of tangling math inside window code.

Simple Analogy: Stock.java is an ID card for a single stock. It doesn't know anything about windows, colors, or buttons—it only knows its own numbers and whether its price swing is safe or dangerous.

Key Points in Simple Terms

  • Separate Data from UI: Stock.java doesn't even import javax.swing.*! Keeping data classes independent makes your code much easier to test, read, and reuse.
  • Use an enum for fixed states: Instead of error-prone strings like "critical" vs "CRTICAL" (typos!), enum AlarmLevel { NORMAL, WARNING, CRITICAL } restricts values to 3 exact choices checked by the compiler.
  • Calculate derived rules automatically in the constructor: Whenever a new Stock(...) is created, it immediately runs computeAlarm() so the alarm level can never get out of sync with change:
    • CRITICAL: price dropped by 100+ (<= -100) or jumped by 200+ (>= 200).
    • WARNING: price dropped by 30+ (<= -30) or jumped by 100+ (>= 100).
    • NORMAL: anything gentler in between.
  • Encapsulation (Private fields + Getters, no Setters): Fields like price are private so outside code cannot accidentally corrupt them (for example, changing change without recalculating alarmLevel). To update a stock, you create a fresh Stock object.

From Your Code

public enum AlarmLevel {
    NORMAL, WARNING, CRITICAL
}

private AlarmLevel computeAlarm() {
    if (change <= -100 || change >= 200) return AlarmLevel.CRITICAL;
    if (change <= -30  || change >= 100) return AlarmLevel.WARNING;
    return AlarmLevel.NORMAL;
}

Showing Data in a Table (JTable, DefaultTableModel & JScrollPane)

Simple goal: Display a list of stocks in neat rows and columns with headers and scrollbars.

Simple Analogy: Swing splits tables into two jobs: DefaultTableModel is the Excel file holding the numbers, and JTable is the monitor displaying that file. When you change a number in the model, the table automatically updates on screen.

Key Points in Simple Terms

  • Model vs. View split:
    • DefaultTableModel stores column names ("Symbol", "Price", etc.) and row data. You add rows with tableModel.addRow(new Object[]{ ... }).
    • JTable takes that model (new JTable(tableModel)) and draws the grid on screen.
  • Always wrap JTable inside a JScrollPane: Notice add(new JScrollPane(table), BorderLayout.CENTER). In Swing, if you add a JTable directly to a window without a JScrollPane, the column header row ("Symbol", "Price"...) won't even show up, and overflowing rows won't scroll!
  • BorderLayout.CENTER makes the table fill the window: Every JFrame uses BorderLayout by default (North, South, East, West, Center). Putting the scroll pane in CENTER makes the table automatically stretch when you resize the window.
  • Easy visual polish: table.setFont(...) and table.setRowHeight(24) make rows comfortable to read instead of cramped.
  • Smart starter test data: Look at your 5 starter stocks in buildTable(): MSMI has change -45.0 (Warning) and FOLD has change 200.0 (Critical), so you immediately see all 3 states on startup!

From Your Code

String[] columns = {"Symbol", "Price", "Change", "Volume", "Alarm"};
tableModel = new DefaultTableModel(columns, 0); // 0 = start with zero rows

for (Stock s : stocks) {
    tableModel.addRow(new Object[]{
        s.getSymbol(), s.getPrice(), s.getChange(), s.getVolume(), s.getAlarmLevel()
    });
}

table = new JTable(tableModel);
add(new JScrollPane(table), BorderLayout.CENTER); // Gives headers + scrollbars + auto-resize
Common Mistake to Avoid: Calling add(table) instead of add(new JScrollPane(table))—the #1 reason beginners wonder "Where did my column titles go?!"

Custom Row Coloring (DefaultTableCellRenderer)

Simple goal: Color entire rows Red for Critical stocks, Yellow for Warning stocks, and White for Normal stocks.

Simple Analogy: If a table has 10,000 cells, creating 10,000 separate label objects would waste tons of memory. Instead, Swing uses one single "rubber stamp" (AlarmCellRenderer): for each cell, it dips the stamp in the right color, stamps that cell onto the screen, and moves to the next cell!

Key Points in Simple Terms

  • Extend DefaultTableCellRenderer: Instead of painting pixels from scratch, you extend Swing's built-in cell renderer and override getTableCellRendererComponent(...).
  • Always call super.getTableCellRendererComponent(...) first: That parent call puts the cell's text, font, border, and selection colors in place. Then you only tweak the background color!
  • Look up the row's alarm level: Using the row index passed by Swing, stocks.get(row).getAlarmLevel() checks the alarm status of that whole stock row—so every column in row 2 gets colored red, not just the "Alarm" column.
  • Respect if (!isSelected): When a user clicks a row to select it, Swing highlights that row in selection blue. Checking if (!isSelected) prevents your white/yellow/red background from hiding the user's click highlight!
  • Always include a default: Color.WHITE case: Remember the "rubber stamp" analogy! Because the same component is reused for every cell, if row 1 painted the stamp Red and row 2 didn't reset it back to Color.WHITE, row 2 would accidentally get stamped Red too!
  • Attach to every column: In StockApp.java, a small loop attaches the renderer to columns 0..4 via table.getColumnModel().getColumn(i).setCellRenderer(renderer).

From Your Code

Component c = super.getTableCellRendererComponent(
        table, value, isSelected, hasFocus, row, column);

Stock.AlarmLevel level = stocks.get(row).getAlarmLevel();

if (!isSelected) {
    switch (level) {
        case CRITICAL: c.setBackground(new Color(255, 100, 100)); break; // Soft Red
        case WARNING:  c.setBackground(new Color(255, 220, 100)); break; // Soft Yellow
        default:       c.setBackground(Color.WHITE); break;              // Reset stamp!
    }
}
return c;

Live Background Updates & Thread Safety

Simple goal: Update stock prices automatically every 1 second in the background without freezing the window or crashing Swing.

Simple Analogy: Imagine a restaurant with one waiter (the UI Thread / EDT) who takes customer clicks and draws the screen. If that waiter stands in the kitchen waiting 1 second at a time (Thread.sleep), nobody can click menus or move the window—the whole app freezes! Instead, you hire a kitchen timer helper (ScheduledExecutorService) to calculate new prices in the back, and pass tiny sticky notes (SwingUtilities.invokeLater) to the waiter to update the screen.

Key Points in Simple Terms

  • Swing's Two Golden Thread Rules:
    1. Never do slow or repeating waits on the UI thread (or the window freezes and stops responding).
    2. Never modify Swing components directly from a background thread (Swing is not thread-safe; always hop back to the UI thread first).
  • ScheduledExecutorService runs code on a schedule: Executors.newSingleThreadScheduledExecutor() creates one background worker, and scheduleAtFixedRate(..., 1, 1, TimeUnit.SECONDS) waits 1 second, then calls updatePrices() every 1 second.
  • SwingUtilities.invokeLater(...) safely updates the table: Once the new price is calculated on the background thread, invokeLater queues a tiny task onto the UI thread to call tableModel.setValueAt(newValue, row, column).
  • Why call table.repaint()? setValueAt updates cells in columns 1, 2, and 4, which only repaints those specific cells. Calling table.repaint() tells the whole table (including columns 0 "Symbol" and 3 "Volume") to redraw immediately if a row's alarm color just changed!
  • Why final int row = i; and final Stock s = updated;? Because the for loop keeps moving to the next stock (i++) before invokeLater runs on the UI thread, Java requires variables captured inside an anonymous inner class (new Runnable()) to be final snapshots of that exact loop step.

From Your Code

private void startLiveFeed() {
    executor = Executors.newSingleThreadScheduledExecutor();
    executor.scheduleAtFixedRate(new Runnable() {
        public void run() {
            updatePrices(); // Runs in the background every 1 second
        }
    }, 1, 1, TimeUnit.SECONDS);
}

// Inside updatePrices(): hop back to the UI thread to touch the table
final int row = i;
final Stock s = updated;
SwingUtilities.invokeLater(new Runnable() {
    public void run() {
        tableModel.setValueAt(s.getPrice(), row, 1);
        tableModel.setValueAt(s.getChange(), row, 2);
        tableModel.setValueAt(s.getAlarmLevel(), row, 4);
        table.repaint();
    }
});
Extra Thread-Safety Tip for Step 2: Right now stocks.set(i, updated) happens just before invokeLater, while AlarmCellRenderer reads stocks.get(row) on the UI thread. Moving stocks.set(row, s) inside SwingUtilities.invokeLater guarantees both reading and writing of stocks happen on the exact same UI thread!

Quick Self-Check (1 Question per Lesson)

Try answering in your head first, then click each question to check!

1. What happens if you forget setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE)?
Clicking the window's X button only hides the window—the Java program (and your 1-second background timer!) keeps running invisibly in the background.
2. Inside an ActionListener, why did the code write StockApp.this instead of just this?
Because inside new ActionListener() { ... }, plain this refers to the ActionListener object itself. StockApp.this reaches out to the outer JFrame window so the popup dialog centers over your window.
3. Why use enum AlarmLevel instead of Strings like "NORMAL" or "CRITICAL"?
An enum prevents spelling mistakes—Java checks at compile time that only NORMAL, WARNING, or CRITICAL can ever be used.
4. What goes wrong if you add a JTable directly to a JFrame without a JScrollPane?
Two things: you get no scrollbars when there are many rows, and the column headers ("Symbol", "Price", ...) disappear!
5. In AlarmCellRenderer, why must default set the background back to Color.WHITE?
Swing reuses the same renderer object like a rubber stamp for every cell. If a critical row sets the background to red and the next normal row doesn't reset it to white, the normal row would get painted red too!
6. Why can't updatePrices() just use while(true) + Thread.sleep(1000) directly on the UI thread?
Because Swing has only one UI thread (the EDT) for drawing and clicks. Sleeping on it freezes the entire window—menus won't open, rows won't select, and the X button won't even respond.
